### 主観情報なしのテスト予測（v0.47.0・旧来の計算2.7.7-dev・表の版16・2026-10-17）

### 全メーカーの暫定予測（v0.48.0・2026-10-18）

## 新アプリでの予測の実行（段階2-2b）

- 「予測」の画面の「予測を実行」から動かします。予算策定担当（その計画のクライアントの担当でもよい）以上の人が使えます。
- 次の2つの処理が続けて動きます（`Forecast.js`）。
  1. 計算: データ本体から計算用ブックを組み立て、旧来の予測（A-9）を動かし、書き換わったシートの控えを取る
  2. 保存: 計算の間にデータ本体が変わっていないことを確かめてから、控えをデータ本体へ戻す

  - 例外（既定ではない設定）: `CONFIG` の `AI_SCORE_BASIS` を `momentum`（相対位置の変化）にしている計画では、予測（A-9）が `AI_SCORE_HISTORY` を読み、同じ予測が同じ表に書き足します。この表は種に入れていない（予測が書く記録の表）ので、市場の調査（A-4）で調べ直した直後は、何も変えずに 2 回予測しても数字が違うことがあります（1 回目が書いた行を 2 回目が読むため）。既定の `level`（水準）では起きません。

## 毎日の手入れ・バックアップ・異常の通知（v0.23.0・@48 公開済み）

- バックアップは毎日の定時実行でデータ本体の複製を作り、バックアップのフォルダに新しい 14 世代を残します。それより古い複製はアーカイブのフォルダへ移します（名前・ID・中身はそのまま。ゴミ箱には送りません）。アーカイブのフォルダが見つからないときは複製を作る前に止まります。
- 複製（毎日・所有者の `runBackup`・月次・表の列を足す移行の前）は、保存と同じロックの中で取ります（2026-10-13〜。`Backup.js` の `appCopyDataBook_`）。書きかけの保存の控えがあれば、写す前に控えのとおりに書き終えます（保存の前と同じ「続きを書く」仕組み）。書き終えられないとき（控えが読めない・締めた年度の計画など）は**写しを取らずに止めます**。写しには書きかけの印が無いので、書きかけのまま写すと、戻したときに表どうしが食い違ったまま気づけないためです。前の世代はそのまま残り、バックアップの失敗として知らせます（書きかけの控えを片づければ、次の回から取れます）。表の列を足す移行の前の写しだけは、書き終えられなくても写します（移行は見出しに列を足すだけで、控えは移行の後に書き終えるため）。
- 毎日の定時実行のトリガー（`triggerDailyBackup`、3 時ごろ）は、**所有者が画面を開いたときに無ければ自動で作ります**（2026-10-07 村井さん承認。確かめるのは 1 日 1 回・あるトリガーには触らない・トリガーの上限 20 に裏の処理の分の余裕が無ければ作らない・開いたときにバックアップそのものは取らない）。作った・作れなかったことは実行ログ（種類 `BACKUP.ENSURE`）に残ります。自動で作らないようにするときは、スクリプト プロパティ `BACKUP_AUTO_ENABLE` を `false` にします（あるトリガーは消しません）。
- **バックアップと手入れは別の実行です（2026-10-13〜）。** 毎日のトリガー（`triggerDailyBackup`）はバックアップだけを取り、手入れ（古い処理の記録の片付け・監査の鎖の確かめ・途中で止まった操作とエラーの数・古いログのアーカイブ・月次の写し・データ本体の表の整え）は、その 2 分後に 1 回だけ動く裏の処理（`SYSTEM.HOUSEKEEPING`。頼んだ人は所有者。画面からは始められない）で動かします。前は 1 回の実行（上限 6 分）にまとめていて、打ち切られると手入れの結果も知らせも残りませんでした。

## 年度の締め（v0.24.0・@49 公開済み）

- 所有者が `apiOwnerTask` の `yearPreview` で今年度より前の年度を確かめ（`canClose`・計画の数 `planCount`・行の数 `rowCount`・控えの大きさ `bytes`・指紋 `inputHash`）、その `inputHash` を渡して `yearClose` で締めます（裏の処理として動きます。`OWNER_TASK` が `jobStatus` に置き換わるので、もう一度実行すると結果が分かります）。今年度や未来の年度は締められません。手順は「所有者の操作（エディタから）」にあります（「記録と状態」の画面は 2026-10-06 に外しました）。
- 締めると、その年度の計画と関係する表の行を写した年度の控え（JSON・上限 8MB）をアーカイブのフォルダへ 1 ファイル残し、読み直して一致を確かめてから、年度を閉じた記録を 1 行だけ足します。**元の行は動かさず・消さず・隠さず**、その年度は全部の書き込み経路で読み取り専用になります（画面には「凍結」の印が出ます）。開き直す操作はありません。
- 締められるには、その年度の全部の計画に承認済みの公式版が要ります。保存の控え・承認待ち・動いている処理があると止まります。自動では締めません。実際の年度を締める操作はまだしていません。

**A-4 の守り**（2026-10-13 の点検。村井さん承認。画面から始めても自動でも同じ）

- **出典の無い主張は数字に効かせない**: Web の出典（根拠の URL）が 0 件か Web 検索が失敗した話題の出来事（event 行）は、向き 横ばい・強さ 0・確からしさ 0・点数 0 で残し、根拠の欄の頭に「出典が見つからなかったため、予測には効かせていません（AI の見立て: 上向き・強さ 80）。」と書きます。購入レポート（Vertex AI Search）の材料が無い（設定なし・失敗・文書も出典も 0 件）話題の比べ（benchmark 行）も、相対位置を空・確からしさ 0・点数 0 にします。旧来の記録（`step3a_status`）に `unsourced_topics=[…]` を足します。AI への頼み方も、出典が無ければ「中立・0」と書いてよい形にしました。
- **AI の文を数式にしない**: AI や Web の文が `=` `+` `-` `@` で始まるときは、そのセルの書式を文字にしてから書きます（旧来の A-4 が書く全部の所）。新アプリは保存の前にも、計算用ブックの `AI_RESEARCH`・`AI_RESEARCH_STRUCTURED` に数式が 1 つでもあれば保存せずに止めます（前の結果を残す）。
- **欠けた話題で上書きしない**: 時間の区切りで止まっていないのに問い合わせが失敗し、4 つの話題（市場・競合・販路・DX）のどれかが無いときは、保存せずに止めます（「（市場・DX）を調べられませんでした。前の結果を残しました。…」）。失敗の無い欠け（答えが読めない）は今までどおり、残った話題で書き直します。
- **手で始めるのは計画ごとに 1 日 3 回まで**（日本の日付。自動の調べは数えません。控えは Script Properties の `APP_AI_MANUAL`）。
- **やり直しは控えた答えを使う**: 同じ計画の A-4 を 6 時間以内に始めていて、その回が保存まで終わっていない（失敗・途中で止まった）ときは、その回の番号と時刻を引き継ぎ、控えた答えを使います（同じ問い合わせにもう一度費用をかけない）。前に控えた失敗の答え（403 など）は使わずに問い合わせ直します。保存まで終わった回の後は、新しい回で調べ直します。

## 所有者の操作（エディタから）

管理の画面（設定・メンバーと役割・表示名・記録と状態・年度の締め・計画の作成・全計画での学習）は画面から完全に外します（2026-10-06 村井さん決定）。これらの操作は、所有者が Apps Script のエディタから `apiOwnerTask` で行います（`OwnerTask.js`）。エディタから実行する関数には引数を渡せないので、頼む操作はスクリプト プロパティ `OWNER_TASK` に JSON で書きます。

**先に読む注意**

- **値の置き場は 2 つです（2026-10-13〜）。** エディタの「スクリプト プロパティ」に残すのは、所有者が手で書くものと、初期設定で 1 度だけ決まるものだけです。アプリが動くたびに書き換える状態は、所有者の UserProperties（所有者のアカウントだけの置き場。エディタの画面には出ません）に置きます。エディタで「スクリプト プロパティを保存」しても、アプリの状態（監査の鎖の最新のハッシュ・書きかけの保存の控え・裏の処理の記録など）を古い値に戻すことはありません（振り分けは `Store.js` の `appProps_`）。

  | 置き場 | キー | 所有者は |
  |---|---|---|
  | スクリプト プロパティ | `OWNER_TASK` | 書く（頼む操作。うまくいくとアプリが消すか `jobStatus` に置き換える） |
  | スクリプト プロパティ | `OWNER_TASK_RESULT` | 読むだけ（アプリが結果を書く。古い値に戻しても、結果の表示が古くなるだけ） |
  | スクリプト プロパティ | `AUTO_RESEARCH_ENABLED`・`BACKUP_AUTO_ENABLE` | 止めるときだけ書く（止めるスイッチ） |
  | スクリプト プロパティ | `APP_FOLDER_ID`・`APP_DATA_SPREADSHEET_ID`・`APP_BACKUP_FOLDER_ID`・`APP_ARCHIVE_FOLDER_ID`・`APP_INTERNAL_DOMAIN` | 触らない（初期設定が 1 度だけ書き、その後アプリは書き換えない。変えると別のファイルを開いたり、社内の人の判定が変わったりする） |
  | 所有者の UserProperties | ほかの `APP_` で始まるキー全部（監査の鎖の最新のハッシュ `APP_AUDIT_LAST_HASH`・書きかけの保存の控え `APP_WRITE_JOURNAL`・裏の処理の記録 `APP_JOB_…`・年度ごとのログのファイル `APP_LOG_SPREADSHEETS_JSON`・手入れの結果 `APP_HOUSEKEEPING`・自動の調べの状態 `APP_AUTO_RESEARCH`・一度だけの写しの控え `APP_BACKFILLS` など） | 触れない（エディタの画面に出ない）。中身は `health`・`listAudit` で見る |

- **一度だけの移し替え**: この版を公開した後の最初の操作（画面を開く・トリガー・エディタからの実行のどれでも）が、スクリプト プロパティにあったアプリの状態を UserProperties へ写し、写せたキーだけをスクリプト プロパティから消します（ロックの中。監査の鎖の最新のハッシュも同じ）。済んだ印は UserProperties の `APP_PROPS_MOVED`、写したキーの名前は実行ログ（種類 `PROPS.MOVE`）に残ります（値は残しません）。途中で止まっても、元はスクリプト プロパティに残るので、次の操作が続きから行います。
- 移し替えの後に、スクリプト プロパティへ上の 5 つ以外の `APP_` で始まるキーが現れても（前の版のコードが動いた・手で足した）、アプリは読みません。消さずに開発者に知らせてください。
- **アプリを動かすアカウントを替えるとき（将来）**: UserProperties は人ごとの置き場で、ほかのアカウントには移りません。Web アプリの「次のユーザーとして実行」・トリガー・エディタから実行する人を別のアカウントにすると、新しいアカウントからは監査の鎖の最新のハッシュ・年度ごとのログのファイルの一覧・書きかけの保存の控え・処理の記録が見えず、監査の鎖が切れて見える・同じ年度のログのファイルをもう 1 つ作る・書きかけの保存を書き終えられない、といったことになります。そのため、初期設定が済んでいるのに UserProperties が空で写すものも無いアカウントで動くと、アプリは空の状態で進まずに止まります（「この実行のアカウントには、アプリの状態…がありません」。スクリプトの編集権限を持つ別の人がエディタから実行したときも同じ）。替える前に開発者に相談してください（前のアカウントの UserProperties の値をスクリプト プロパティへ書き出せば、新しいアカウントで印 `APP_PROPS_MOVED` が無い最初の実行が上の移し替えで取り込みます。書き出す操作はまだありません）。
- **スクリプト プロパティを保存する前に、画面を読み直してください。** 「スクリプト プロパティを保存」は、編集の画面を開いたときの値を全部書き戻すおそれがあります（実際の動きはまだ確かめていません）。アプリの状態はもう入っていませんが、`OWNER_TASK` はアプリが消したり `jobStatus` に置き換えたりするので、古い画面のまま保存すると、済んだ頼みが戻って同じ操作をもう一度動かすことがあります。処理を始めると `OWNER_TASK` は自動で `jobStatus` に置き換わるので、結果はプロパティを触らずに `apiOwnerTask` をもう一度実行すれば分かります。
- **スクリプトの編集権限がある人は、エディタから実行すると所有者として扱われます。** Apps Script では、エディタから実行した人がそのまま実行する人になるためです（`apiSetup` など、所有者だけの入口も同じです）。スクリプトの編集権限は所有者だけにしてください。画面（ウェブアプリ）から呼ばれた場合など、実行する人が所有者でなければ断り、断ったことを記録に残します。

**手順**

1. Apps Script のエディタで「Trends2Targets」のプロジェクトを開きます。
2. 左の「プロジェクトの設定」（歯車）を開き、いちばん下の「スクリプト プロパティ」で「スクリプト プロパティを編集」→「スクリプト プロパティを追加」を押します。
3. プロパティに `OWNER_TASK`、値に下の表の JSON を 1 行で入れ、「スクリプト プロパティを保存」を押します（すでにあるときは値だけ書き換えます）。
4. 左の「エディタ」で `Api.gs` を開き、上の関数の一覧から `apiOwnerTask` を選んで「実行」を押します。
5. 下の「実行ログ」に結果が出ます。同じ結果（大きいときは要約）がスクリプト プロパティ `OWNER_TASK_RESULT` に入ります（「プロジェクトの設定」を開き直すと見えます）。`"ok": true` ならうまくいっています。`hint` に、すぐに終わったのか、裏の処理を始めたのか（まだ終わっていないのか）が書いてあります。
6. うまくいった後の `OWNER_TASK` は、操作の種類で変わります。
   - 読むだけの操作（`listDirectory`・`listSettings`・`listPlans`・`planCandidates`・`health`・`listAudit`・`yearPreview`・`poolPreview`・`calibrationPreview`・`vertexConfigPreview`・`jobStatus`）: そのまま残ります。もう一度実行すると読み直します。
   - 書く操作（`saveMember`・`grantRole`・`revokeRole`・`saveClientName`・`saveClient`・`saveSetting`・`enableBackup`・`runBackup`・`runHousekeeping`・`verifyAudit`・`setVertexConfig`）: すぐに終わり、`OWNER_TASK` は消えます（同じ操作を 2 度動かさないため）。
   - 裏の処理を始める操作（`createPlan`・`setPeople`・`yearClose`・`poolApply`・`setCalibration`）: `OWNER_TASK` が `{"action":"jobStatus","jobId":"JOB-…"}` に置き換わります。1〜2 分おいて、プロパティは触らずに `apiOwnerTask` をもう一度実行すると、処理の結果（`status` が `DONE` か `FAILED`。`FAILED` なら `error` に理由）が分かります。短い処理は、始めたその場で終わることもあります（`hint` に「すぐに終わりました」と出ます）。
   - 実行している間に `OWNER_TASK` が書き換えられていたときは、消しも置き換えもしません。
7. 失敗したときは `"ok": false` と理由（`error`）が入り、`OWNER_TASK` は残るので、直してもう一度実行します。

**値の写し方**

- 中で使う関数・権限の判定・入力の確かめは、画面の操作と同じです。書く操作は画面と同じ操作の名前（`SETTING.SAVE`・`ROLE.GRANT`・`CLIENT.SAVE` など）で操作の記録に残り、理由の欄に「OWNER_TASK（エディタから）」と入ります。
- `roleId`・`clientId`・`rowVersion` は `listDirectory`、`planId` は `listPlans`、ZAC の名前は `planCandidates` の結果から写します。
- `rowVersion` は、ほかの変更を上書きしないための行の版です。今ある行を書き換える操作では中の関数が必ず確かめます（2026-10-13 から。無いと「画面が古いので、読み直してからもう一度操作してください。」で止まる）。エディタからの頼みで省くと、実行したときの今の版を読んで渡します（`saveMember`・`revokeRole`・`saveClientName`・`unlinkPerson`。`saveClient` で直すときは省けません）。確かめてから書きたいときは `listDirectory` の結果から写します（写した版より新しくなっていれば止まる）。
  - `saveMember` は `members[].rowVersion`、`revokeRole` は `roles[].rowVersion` を写します。
  - `saveClientName` は `clients[].rowVersion`（表示名の行の版。自動の名前に戻した行にもある）を写します。まだ表示名を決めたことがないメーカーだけ空（`""`）です。
  - `saveClient` は `clients[].clientRowVersion`（メーカーの行の版）を写します。
- `saveClient` は、`clientId` を省くとメーカーを足し、`clientId` を入れると直します。直すときは全部の項目（`clientName`・`zacCode`・`isActive`・`note`・`rowVersion`）が要ります（省いた項目が空や有効に戻らないよう、足りなければ何もせずに止まります）。今の値は `listDirectory` の `clients[]`（`zacName`・`zacCode`・`active`・`note`）から写し、変えたい項目だけ変えます。`isActive` は `true` か `false`（`""` で囲まない）です。`clientName` は売上の取り込みで ZAC と照らし合わせる名前なので、画面に出す名前を変えるときは `saveClientName` を使います。
- `createPlan`・`yearPreview`・`yearClose` には年度 `fy`（4 桁の数。例 `2027`）が要ります。無い・4 桁でないときは、何も始めずに止まります。
- 年度の締めは、必ず `yearPreview` で `"canClose": true` を確かめ、出た `inputHash`（64 桁）をそのまま `yearClose` に渡します。確認の後に年度の中身が変わっていれば、締めずに止まります。
- `listAudit` は、`limit` を省くと新しい 200 行までです（最大 2000）。結果が長すぎて実行ログに全部を出せないときは、`OWNER_TASK_RESULT` の `note` にそう書いてあるので、`limit` を小さくするか、`month`・`query` で絞ってもう一度実行します。
- `health` の `ok` は、`warnings` に 1 つでも要確認（表の問題・監査の鎖・監査の最後の行が消えた疑い・バックアップが無効か 26 時間より古い・手入れの要確認・書きかけの保存・年度の一覧を読めない）があれば `false` です。手入れのときの 24 時間のエラーの数（`housekeeping.errors`）と終わりの無い開始の数（`housekeeping.openStarts`）も出ます。

### 計画の補正の値（2026-10-07 村井さん決定）

予測に掛かる補正（旧来の `CALIBRATION_STATE`）は、所有者が承認した値だけを `setCalibration` で書きます（`Calibration.js`）。月次の自動学習（B-5）が学ぶ値は、締まっていない月の実績に引っ張られていたためです。

- 書ける項目（`set` の中。ほかの項目・範囲の外・`""` で囲んだ数は、何もせずに止まります）
  - `bias_correction_factor`: 補正の係数。0.75〜1.25（1 = 補正なし）
  - `residual_month_bias_json`: 暦月ごとの補正。`"{}"`（補正なし）か `"{\"4\":0.05}"` の形（月は 1〜12、値は ±0.2 まで）
  - `auto_update_enabled`: 自動の学び。0 で止める・1 で動かす。0 にすると、B-5 の自動の学びと、承認した見直し案の反映（C-3）の両方が止まります
  - `ai_weight_override`: AI の効き。0〜0.01。0 にすると、予測の AI の倍率（k_ai）はどの月も 1 になり、ほかの層（統計・入力・スポット・補正）は変わりません。`""` で業務の設定（CONFIG の `AI_WEIGHT`）の値に戻します
- `reason`（理由）は必ず入れます（200 字まで。`CALIBRATION_STATE` の `note` と操作の記録に残ります）。
- 変わった項目ごとに `CALIBRATION_HISTORY` へ 1 行を足します（月次の自動学習・見直し案の反映と同じ形。`review_id` は `OWNER-APPROVED`、`changed_by` は所有者）。前の履歴は消しません。戻すときは、履歴の `old_value` をもう一度 `setCalibration` で書きます。
- `withdrawPendingReview` を `true` にすると、一番新しい四半期の見直し案のどの案もまだ反映していなければ取り下げます。判断が保留・却下・承認でも（反映の操作 C-3 を保留のまま動かした後でも）、反映していなければ取り下げます（判断し直して C-3 をもう一度動かせば反映できてしまうためです）。`QUARTERLY_REVIEW_LOG` の行の判断を「取り下げ」にし（判断した日時と人を入れます。`applied` は 0 のまま。行は消しません）、計画の画面でも取り下げた案として出し、承認した見直し案の反映（C-3）でも適用されなくなります（後から判断を保存し直しても同じです）。前の判断と日時は結果の `withdrawn.before` に残ります。案を 1 つでも反映した見直し案と、もう取り下げた見直し案には何もしません（`withdrawn` が `null`）。
- 先に `calibrationPreview` で今の値と取り下げる見直し案（`pending`。今の判断 `decisions` と判断の日時 `decidedAt` も出ます。取り下げるものが無ければ `null`）を確かめ、出た `inputHash` を渡すと、確かめた後に計画が変わっていれば書かずに止まります（省くと、実行したときの今の指紋を読んで渡します。計画への保存は 2026-10-13 から指紋が必須。`setPeople` も同じ）。
- 変わる値が無ければ何も書きません（同じ頼みを 2 度動かしても、履歴は増えません）。締めた年度の計画には書けません。所有者だけの操作です（管理者の役割があっても、ほかの人は画面からも始められません）。
- 結果（`jobStatus` の `result.result`）に、前と後の値（`changed`）・変えなかった項目（`unchanged`）・取り下げた見直し案（`withdrawn`）・書いた後の値の注意（`warnings`）が出ます。

### AI 調査の問い合わせ先（2026-10-13 村井さん承認）

A-4 が問い合わせる Vertex のモデル名・リージョン・プロジェクトは、計画を作るときに旧来の既定値（`gemini-3.8-flash`・`global`・`forecast-agent-498907`）が各計画の CONFIG に写されます。モデルが廃止されると全計画の A-4 が失敗するので、所有者が全計画まとめて替えられるようにしました（`Ai.js`）。

- 先に `vertexConfigPreview` で、計画ごとの今の値（`plans[]` の `model`・`location`・`project`。年度を締めた計画は `frozen: true`、CONFIG に行が無ければ `missingRows`）と、締めていない年度の計画での値ごとの数（`summary`）を確かめます。
- `setVertexConfig` の項目: `model`（必須。英小文字・数字・`.`・`-` の 3〜61 字）・`location`（省ける。例 `global`・`asia-northeast1`）・`project`（省ける。Google Cloud のプロジェクト ID）・`planIds`（省ける。`listPlans` の `planId` の配列）。形の違う値・ほかの項目は、何もせずに止まります。
- `planIds` を省くと、年度を締めていない全計画に書きます。年度を締めた計画を名指ししたら、何も書かずに断ります。
- 計画ごとにデータ本体の CONFIG の行を書き換えます（ロックと保存の控えの中で。ほかの保存と同じ書き方）。変わる値が無い計画は書きません（同じ頼みを 2 度動かしても書きません）。CONFIG に行が無い・元どおりに組み立てられない計画は書かずに `skipped` に理由を返します。4 分を過ぎたら残りの計画は書かずに `remaining` に返すので、同じ頼みをもう一度動かします。
- 結果（`changed` に計画ごとの前と後の値・`unchanged`・`skipped`・`remaining`）は、操作の記録（`VERTEX.SET`）の終わりの行にも残ります。
- 書いた計画は入力の指紋が変わるので、開いていた画面の保存は断られ（開き直す）、次の操作で計算用ブックを組み立て直します。CONFIG は予測の乱数の種が見る表なので、次の予測の数字は少し動きます。これから作る計画には旧来の既定値が写されるので、作った後にもう一度 `setVertexConfig` を動かします。

`{"action":"setVertexConfig","model":"gemini-3.8-flash","location":"global"}`

## 利用者・管理者の運用手順

現在は所有者だけが開けます（MYSELF）。役割の判定はローカルで検証済みですが、社内の複数人での実運用は未確認です。

| 役割 | 画面と操作 |
|---|---|
| 閲覧・情報提供 | ホーム・メーカー・予測（予測・予算・根拠・検証・公式版）・分析・学びを読む。入力の保存は予算策定担当以上です |
| 予算策定担当 | 入力と予算を保存、予測を実行、公式版として出す、検証と月次学習を更新。クライアント限定の付与では対象の計画だけ書けます |
| 承認者 | 公式版を承認・却下、四半期レビューを判断・適用。既存の役割階層では予算策定担当の操作も含みます |

### 1 年の流れ

1. 所有者が `apiOwnerTask` で、必要なメーカー（`saveClient`）と計画（`createPlan`。年度と担当者）を登録します。年度は4月開始の年で呼びます（FY2026 は2026/04〜2027/03）。
2. 管理者が「進み」で売上取込（A-2）、策定担当が売上加工（A-3）・AI調査（A-4）を実行します。実績の取得元は、所有者が `saveSetting` で決めた業務の設定（ZAC の実績のスプレッドシート）を使います。
3. 策定担当が入力・予測・予算を整え、「公式版」で提出します。承認者が数字を確認して承認・却下します（自分の提出を承認する扱いは既存ルールに従います）。
4. 実績が締まったら（月末から 5 日たち、前の月の ZAC の計上が終わってから。「暫定実績・着地見込み・見通しの空模様」の注意）管理者が「検証」で実績取込（B-1）、策定担当が検証更新・指標更新・見立て更新・月次学習（B-2〜B-5）を順に行います（B-2 で数字が変わった月の外れた月の振り返りは、B-4 まで出ません。B-2 と B-4 は続けて）。インサイトの記入も保存します。
5. 四半期ごとに提案を作り（C-1）、承認者が判断し、承認した提案を適用します（C-3）。C-1 は学びの仕組みを直すまで止めています（2026-10-07 村井さん決定）。補正の値は、所有者が `apiOwnerTask` の `setCalibration` で承認した値を書きます。
6. 次年度は新しい計画として作ります。終わった年度を締める場合だけ、所有者が `apiOwnerTask` の `yearPreview` で内容を確認し、`yearClose` で年度を締めます。現在・未来の年度は締めません。行の移動・凍結解除は行いません。

### 管理者の点検と障害対応

- 所有者が `apiOwnerTask` の `saveMember`・`grantRole`・`revokeRole` で社内のメンバーと役割を登録し、`listDirectory` で役割・対象メーカー・有効期間（`validFrom`・`validTo`）を確認します。所有者は常に管理者です。付与の無効化と公開範囲の変更は別の操作です。
- 所有者が `apiOwnerTask` の `health` で保存の控え、処理、監査、バックアップ、手入れを確認し、`listAudit` で操作の記録・実行ログ・エラーを見ます。処理中の重複依頼は断られるので、終わったのを確かめてから（画面は読み直す。エディタからは `jobStatus`）再試行します。古い画面で保存が止まった場合も読み直します。
- 書きかけの保存は、控えの内容を確認して予測の画面の「保存の続きを書く」で復旧します（全体の予算策定担当以上の権限が必要）。凍結記録や控えが壊れている場合は書き込みを止めたままにし、控えを削除して強行しません。
- 日次バックアップは新しい14世代をバックアップフォルダに残し、古い世代と月次の写しはアーカイブに残します。正常な日は通知メールを送りません。通知の権限確認は前の節の `appAuthorizeMaintenance_` を使い、配送確認のために無断のテストメールや意図的な障害を起こしません。

### バックアップからの復元

自動復元の操作は未実装です。まず現在のデータと凍結記録を別の控えとして保全し、復元候補の年度・計画・列・キー・型・数式・書式・凍結記録を読み取りだけで照合します。古いバックアップには年度の締めの記録が無い可能性があるため、丸ごとの差し戻しで締めた年度を開かないようにします。

データ本体の差し替え、保存先の切り替え、行の書き戻しは、具体的な復元設計と村井さんの承認後に行います。凍結記録の表が読めない場合は空で作り直さず、元の記録を戻す方針を先に確認します。元データ・候補ファイルは削除・ゴミ箱送りをしません。

## コードの約束

- 公開する関数（ブラウザから `google.script.run` で呼べる関数）は `Api.js` の `doGet`・`api*`・`trigger*` だけ。どれも本体は `return api_(...)` だけにし、本人確認 → 役割 → 記録つき実行 → エラーの記録 を必ず通す。それ以外の関数は名前の末尾を `_` にする。`trigger*` は、このプロジェクトのその入口のトリガー（`triggerRunJob` は待ち行列の処理のトリガー）の UID のときだけ受け付けて所有者として動かす。管理者や所有者がブラウザから呼んでも断る（2026-10-13。前は管理者なら呼べ、毎日の処理の知らせのメールや AI 調査を動かせた）。
- 今ある行・計画を書き換える操作は、楽観ロックの印が必須（2026-10-13。省くと後から書いた方が勝っていた）: 行の版 `rowVersion`（`Store.js` の `appUpdateByKey_`。仕組みの中の書き直しだけ `APP_ROW_UNCHECKED`）・計画への保存（`PLAN.EDIT`）と公式版を出す（`VERSION.SUBMIT`）は開いたときの指紋 `inputHash`・判断（`VERSION.DECIDE`）は版の `rowVersion`。新しく作る操作には要らない。無いときは「画面が古いので、読み直してからもう一度操作してください。」。
- 書き込みは開始を記録できなければ実行しない（fail-closed）。記録はハッシュの鎖でつなぎ、所有者が `apiOwnerTask` の `health`（今月）・`verifyAudit`（全部の月）で改ざんを点検できる。
- 値（Script Properties・所有者の UserProperties）の読み書きは `Store.js` の `appProps_()` だけを通す（キーごとに置き場を振り分ける。`app/tests/app-props-store.test.mjs` が見張る）。アプリの状態のキーは `APP_` で始める（UserProperties に入る）。
- 表の列は `Schema.js` だけで決める。データ本体の 1 行目が定義と違えば書き込みを止める。列を変えるときは版を上げて移行する（列は後ろに足すだけ。`APP_ADDED_COLUMNS` に書くと、最初の操作が移す）。
- `Assets.js` は自動生成（`cd ../assets/characters/src && python3 build.py`）。手で編集しない。
