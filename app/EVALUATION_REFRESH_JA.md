# 実績・採点・原因整理を安全に更新する手順

2026-11-01 作成。公開 @143・ソース `1b15221`（実績更新の `22ecc01` を含む）の所有者操作に対応する手順。最終8シートメタ検査も公開143へ反映し、固定版57ファイルのbyte一致と全125テストの通過を確認した。個別の取込元・ID・金額を含む完全な証跡は非公開で保持し、末尾には一般化した確認結果のみ記す。

指定した開いている年度の1計画について、B-1 実績取込 → B-2 現行基準の採点 → B-4 原因整理を1つずつ進める。予測の再実行、予算の保存、採点方針の書換えはこの手順に含めない。取込元・対象計画・退避版・照合結果の実値は非公開の実施記録に残す。

## 1. 取込条件と全データの退避

所有者として、次を確認する。

- 対象のメーカー・FY・計画IDと、設定 `source.zac_spreadsheet` の実際の取込元が一致している。A-2 売上取込が成功しており、B-2に進む計画には保存済みの予測実行がある。
- 年度が締められていない。未完了のJournal、待機中・実行中のジョブ、有効な一括処理がない。これらがあれば、保全照合は開始できない。
- データ本体の **全シートを含むnative Google Sheetsのコピー** を作る。元とコピーはともに操作する所有者の所有、共有範囲は非公開、追加の編集者・閲覧者なし、単一の同じ親フォルダに置く。データ本体自身を退避版に指定しない。照合のために共有設定を変更する必要はない。
- コピーの取得日時、元とコピーのID、共有状態を非公開の実施記録へ残し、元とコピーを保持する。1計画分だけの書出しやCSVは、全データの退避版の代わりにはならない。

B-1は、CONFIGのメーカーとFYを使い、設定された元ブックの `*` で始まり `_actual_value` で終わる表を読む。FY開始の3年前の4月からFY終了の3月までの48か月が対象で、最新の表名だけには限定しない。元行を分類・日付・金額で選別するため、照合も同じ条件で行う。元データの重複行を自動で除去する処理はない。

締まりは日本時間の月末から5日後で判定し、各行の取込日時にも残す。例えば11月1日の取込では10月はまだ締め前になる。採点には、締まった実績に加え、**対象月が始まる前に実際に保存された予測** が必要である。`actual_closed` の予測や、旧形式で実績と同額の予測は除外される。今から予測を再実行して過去月の事前予測を補うことはできない。

## 2. 実行前の完全一致を確認する

以下のJSONはひな形。`<...>` を非公開で確認した実値へ置き換え、Apps Scriptのスクリプトプロパティ `OWNER_TASK` に設定して、所有者として `apiOwnerTask` を実行する。

```json
{
  "action": "evaluationPreservation",
  "planId": "<対象計画ID>",
  "backupId": "<全データ退避版ID>",
  "verify": false
}
```

`preserved:true`、`exact:true`、`verified:false` と、元と退避版の全表の一致を確認する。`checkedTables` は退避時に実在した表の数であり、固定数を前提にしない。未作成の任意表は作らず、定義から外れた旧表も含めて比較する。

返された64桁の `inputHash` を次のB-1に明示して使う。各B処理の入口では省略時に現在値を補えるが、この手順では、確認した指紋を省略しない。確認後に計画のデータが変われば、ジョブ開始前または最初の組立・計算・保存の段階で停止する。

所有者操作の結果は `OWNER_TASK_RESULT` と実行ログに残る。全表の指紋を含む結果はプロパティの容量を超えて要約されることがあるため、**全表の証跡は完全な実行ログまたは完全な返値から非公開で保全する**。要約に出た一部の表だけで全表一致と判断しない。

保全照合はデータ本体・退避版へ書き込まない。`OWNER_TASK_RESULT` や操作ログなど、既存の管理用記録は更新される。

## 3. B-1 → B-2 → B-4を個別に進める

### B-1 実績取込

```json
{
  "action": "importActuals",
  "planId": "<対象計画ID>",
  "inputHash": "<実行前の完全一致確認で得たinputHash>"
}
```

開始すると `OWNER_TASK` は `jobStatus` とジョブIDの組に置き換わる。そのまま `apiOwnerTask` を再実行し、**最終状態が `DONE` になり、結果の計画・操作が今回の要求と一致するまで待つ**。元のジョブIDから続きの段もたどる。`QUEUED`、`RUNNING`、`CONTINUED` は完了ではない。`FAILED`、`STALLED`、`LOST` や結果不明のまま、次の処理を開始しない。

B-1完了後は、保存されたnative `ACTUAL_EVAL_MONTHLY` の対象計画分を全件読み戻し、同じ取込条件で読んだ元データと照合する。メーカー、FYの範囲、月別・分類別の件数と合計、全体件数、締まりと取込日時を確認する。事前に求めた元データの集計は見込みであり、実取込後の読戻しで確定する。元データが照合中に更新された場合も、差の原因を確定してから進む。

保存済み実績がある計画を0件で置換する場合は、保存前に拒否して既存実績を残す。件数の急減や一部欠落をすべて自動検知する仕組みではないため、0件・急減・照合不一致があれば後続処理を止め、取込元を確認する。

次の保全照合を実行し、`preserved:true`、`verified:true` を確認する。退避版は最初に作った同じ全データコピーを使う。

```json
{
  "action": "evaluationPreservation",
  "planId": "<対象計画ID>",
  "backupId": "<最初の全データ退避版ID>",
  "verify": true
}
```

### B-2 現行基準の採点

直前の `verify:true` が返した最新の `inputHash` を使う。

```json
{
  "action": "runEvalReport",
  "planId": "<対象計画ID>",
  "inputHash": "<B-1後の保全照合で得たinputHash>"
}
```

`jobStatus` で最終 `DONE` を確認し、native `EVAL_LOG` と `EVAL_COMPARE_MONTHLY`、`RUN_LOG` の現行方針・採点月数・締め前の月・事前予測なしの記録を読む。実績があっても、事前予測の条件を満たす月がなければ採点0件はあり得る。旧行の方針だけを書き換えて採点済みにしない。

B-2の末尾には既存の自動学習がある。`auto_update_enabled` が有効で必要な有効月数があれば、`CALIBRATION_STATE` と `CALIBRATION_HISTORY` が更新され、将来の予測に使う補正が変わり得る。この手順のために設定を変更せず、補正の変更またはスキップ理由を個別に記録する。B-2の完了だけでは、自動学習の成功まで保証しない。

再び同じ退避版に対して `evaluationPreservation` の `verify:true` を実行し、保全結果と最新の `inputHash` を取得する。

### B-4 原因整理

```json
{
  "action": "runEvalInsights",
  "planId": "<対象計画ID>",
  "inputHash": "<B-2後の保全照合で得たinputHash>"
}
```

`jobStatus` で最終 `DONE` を確認し、native `EVAL_INSIGHTS` と実行記録を読み戻す。その後、同じ退避版に対する `evaluationPreservation` の `verify:true` をもう一度実行する。各段階の完全な照合結果・指紋・ジョブID・操作結果を非公開の実施記録へ残す。

### 最終8シートの復元メタを別実行で確認する

全表の保全照合が終わった後、次の読取専用操作を **別の実行** として行う。実行中のジョブ・未完了Journal・有効な一括処理がないことを、ここでも確認する。

```json
{
  "action": "checkEvaluationMetadata",
  "planId": "<対象計画ID>"
}
```

検証用8シートに対応するnativeの8表と `ENG_SHEETS`・`ENG_ROWS`・`ENG_FORMATS` の計11物理表が存在し、定義の見出しと行を読めることを先に確認する。その後、実際に保存された行・型・表示形式・寸法から8シートの復元メタを計算し、保存済みメタと全て一致する場合だけ `matched:true`、`checkedSheets:8`、`storeWrites:0` を返す。

内部計算が不一致を示すpatch候補を返しても、自動で適用しない。1シートでも不一致・欠落・計算エラーがあれば停止し、記録と退避版を保持して原因を調べる。この検査が成功しても、全表の前後保全照合や取込元との業務値の照合を省略できるものではない。

最後に通常画面の「予測準備」から対象計画を開き、「人の記入」の対象月・理由・確認した記録が保存済みデータと一致することを確認する。表示確認のために仮の記入や保存を行う必要はない。書込可能な人と読み取り専用の人、締め済み年度の扱いは従来の権限による。

## 4. 変わる記録と保持する記録

| 処理 | 更新を許す既存の業務表 |
| --- | --- |
| B-1 | `ACTUAL_EVAL_MONTHLY`、`PROCESS_STATUS`、`RUN_LOG` |
| B-2 | `EVAL_LOG`、`EVAL_COMPARE_MONTHLY`、`PROCESS_STATUS`、`RUN_LOG`、自動学習の `CALIBRATION_STATE`・`CALIBRATION_HISTORY` |
| B-4 | `EVAL_INSIGHTS`、`PROCESS_STATUS`、`RUN_LOG` |

上記表に対応するnativeの保存メタ・行・表示形式、各処理の `PLAN_ACTIONS`、B-2による `HIT_RECORDS` の追記も照合対象となる。既存の追記記録の変更は許さない。

処理対象外の表で値・型・数式が変われば、Journalによる保存を始める前に処理全体を拒否する。計算用ブックの復元時に対象外の表へ表示形式の補完だけが生じた場合は、その表を保存対象から外し、データ本体の元の形式・寸法を保つ。

B-1は対象計画の実績表を置換する。B-2は同じメーカー・月・シナリオの採点を更新し、B-4は同じメーカー・月の機械による原因整理を更新する。旧採点の機械列を原文のまま保持する操作ではなく、更新前の全データコピーが旧状態の根拠となる。再実行では同じ月の行を単純追加し続けないが、取込・採点日時やログは変わるため、byte単位の冪等操作ではない。

B-4は、既存行に人の記入の跡がある場合、値が入った次の7列を保持する。

`cause_hypothesis`、`impacted_assumption`、`action_type`、`next_cycle_reflection`、`owner`、`due_date`、`status`

自動の既定値だけの行は再判定する。空の人入力列には既定値が入ることがあり、`cause_bucket` は機械の列として再生成する。保全照合は既存の行番号キーを保持し、メーカー・対象月の付替えを拒否し、人の非空7列は保存された値・型・数式・形式まで比較する。既存の重複行を手作業で整理することは、この手順に含めない。

他の計画、保存済み予測・予測スナップショット、予算・公式版、業務入力など、許可範囲外の記録を保全する。B-2の補正更新を理由として既存予測を再実行しない。

## 5. 中断と復旧

指紋の不一致、取込元の異常、ジョブの失敗・状態不明、保全照合の失敗があれば、次のB処理へ進まない。開始済みの処理はジョブIDとJournalの状態を確認し、完了したか不明なまま同じ処理を重ねて実行しない。成功した段までのログ、native読戻し、退避版を保持する。

業務ジョブと後段の読取専用照合の実行状態は分ける。照合の結果ログを回収できても、実行全体がFAILED表示なら正常完了の証拠とは扱わず、業務ジョブを重ねずに照合の状態を確認する。

この手順にはB-1/B-2/B-4の変更を一括で巻き戻すコマンドはない。復旧の根拠は最初の全データコピーと前後の照合結果であり、未完了Journal・その後の変更・保存先の整合を含めて復旧手順を決める。照合失敗を自動巻戻しの完了と扱わない。

`rollbackNativeMetadataRepair` は、[保存メタの保全修復](NATIVE_METADATA_REPAIR_JA.md) 専用の巻戻しである。実績・採点・原因整理・自動学習の業務データを戻す用途には使わない。

## 6. 照合結果が保証する範囲

実行前の完全一致は、実在する全表の名前と使用範囲の行列数、値・型・数式・表示形式、locale・time zoneを比較する。実行後は、許可した対象計画の変更だけを通し、保護対象は行の値・型・式・形式と重複数を照合する。nativeの行位置が移動しても、行内のキーを含む内容が同じなら保持と判定する。定義のない旧表は物理順を含めた表全体の指紋を厳密に保持する。

物理シートの `getMaxRows`・`getMaxColumns`、使用範囲外だけの書式、見た目の装飾・ノート・表示順などは全表指紋の保証範囲に含まれない。native `ENG_SHEETS` のセルに保存される仮想シートの寸法は、通常の値として照合される。

保全照合は全表を複数回読む。GASの実行時間上限内に完了するかは実データで確認し、時間切れや結果を取得できなかった照合を成功扱いにしない。照合だけが失敗しても、データ本体・退避版へ書く処理ではない。

ソースの公開版との一致、ジョブの `DONE`、native保存結果の独立読戻し、通常UIの表示確認は、それぞれ別の証拠である。全てを確認した範囲だけ実施結果へ記録し、実顧客名、実際の計画ID・退避版ID・指紋、金額、人の記入原文は公開リポジトリへ載せない。
